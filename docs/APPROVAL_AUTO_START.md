# 立项审批后自动启动

## 使用流程
审批人批准新项目时，可启用“条件齐备后自动启动”，选择仅分析与方案，或分析、开发、测试与预览；批准累计预算以及单轮扫描/迭代预留上限。外部项目可选择加入推广，但每轮推广仍须审批；内部项目永远不包含推广。

批准不会自动创建云资源或赋予现实人员新权限。缺少业务负责人、开发组、产品/工程/运维职责、验收人、执行额度、仓库、环境、材料来源、CDN、执行器能力或可用预算时，项目显示逐项准备清单。技术人员在项目概览中补齐启动配置。后台恢复检查条件，齐备后生成唯一的首轮计划，无需再次立项。

## 授权与边界
- 申请人不能决定批准的自动范围。范围只在有权审批人的决策中冻结，随审批意见和预算留痕。
- 仅分析模式不创建开发、发布和推广任务。开发模式保留发布审批；推广即使纳入范围，也保留推广审批。
- 内部项目还需工程师复核当前自动测试报告，部署后指定使用者验收，才结束本轮并允许下一轮。
- 发布审批等待期间保留原运行和预算，不取消重建。停止及审批驳回不会被下一次心跳自动恢复。
- 失败重试耗尽、执行步数超限、超预算会暂停并要求负责人处理。状态不明的外部作业只核对原编号，不重复提交。
- 系统按批准的真实项目预算台账逐笔预留与结算；本地运行额度不能覆盖项目累计预算。
- 旧项目不会因本次升级自动开启新授权；没有显式批准启动策略的历史立项保持原行为。

## 后台
每小时的已关联巡检调用 `/api/autonomy/service`。检查自动启动项目后公平选择项目心跳；不需要用户保持页面打开。每个心跳推进一个步骤或核对一个在途作业，不保证在一小时内完成整个开发周期。

调用者先通过 Sites get_site 验证此Site仍为原账户owner且仅owner可访问，再使用其平台服务凭据。应用还校验 XLLOOP_SERVICE_KEY，值为 `xlloop-service-v1:` 加该平台服务凭据SHA256摘要。秘密只保存在Sites运行时配置，不进入代码、前端或任务提示。凭据不匹配时停止并修复配置，不降级认证。

未配置 XLLOOP_RUNNER_URL / XLLOOP_RUNNER_TOKEN 或实际外部模型、仓库、CI、云端环境时，只显示缺口；不假装发生真实开发、部署、推广或业务收益。

## 验证
`node tests/launch.test.mjs` 覆盖审批范围冻结、缺项检查、首次计划去重、技术人员补齐后启动、发布审批等待、内部测试复核与使用者验收、拒绝后暂停、显式恢复、持久停止、未授权成员不能自行启动。所有外部执行均为内存fixture，真实后端心跳另行读取验证。
