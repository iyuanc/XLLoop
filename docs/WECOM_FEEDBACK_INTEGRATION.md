# 企业微信问题与建议：交接与验收

## 已实现

- 站内入口：工作台“问题与建议”，或项目概览“反馈问题”。不增加第五个一级导航。
- 已授权员工提交，返回FB-编号；记录来源、所属项目、标题、具体情况、类型、紧急程度、截图/录屏HTTPS链接。当前支持链接，不提供附件上传。
- 已知项目默认交给有效的项目负责人（manager）；没有负责人或无法分类时由可配置受理人兜底，默认所有者。多位项目负责人时按成员表顺序选第一位，仍可人工改派。
- 指派/排期、补充、处理、提交验收、由提交人验收关闭、未解决重开、人工确认重复、升级处理、转为机会草稿。转机会不等于立项或预算获批。
- 只有提交人、相应项目负责人、经授权处理人、所有者可读；紧急反馈的同项目运维亦可读。全项目访问权限不会自动让所有同事看到全部反馈。
- 原始反馈和处理历史保留。签名桥接消息按事件ID去重；重复请求不重复建单。
- 站内通知已实现；企业微信通知记录待发送/领取中/失败/结果不明/桥接报告已发，发送成功须附供应商回执引用。不将队列记录称作已经送达用户。
- “企业微信问题反馈入口接入与验收”由所有者进入新版后的初始化请求幂等建立，默认由所有者负责。需实际收单、身份映射和发信回执证据后才允许关闭。
- 普通反馈初始目标响应时间48小时、紧急反馈4小时，可由负责人重排目标时间。这是系统目标，不是已承诺的服务SLA。
- 超期在待办统计中显示；后台心跳/所有者进入工作台时检查催办，同一工单最多一天一次，并进入站内通知与待发队列。

## 运行依赖 / 尚未接通

当前没有公司企业微信凭据和真实员工身份映射，也没有部署企业微信官方回调适配器。本仓库提供已鉴权的XLLoop桥接接口，**不是可直接填写到企业微信后台的官方加密回调URL**。

现有Sites后台巡检在本次读取时处于暂停状态。本次不擅自恢复可能派发其它项目工作的旧巡检；因此定时催办和自动分诊需要负责人明确恢复巡检或部署独立服务调度。站内工单和手动推进不依赖该调度开启。

## 对接流程

1. 技术人员在公司控制的服务器部署企业微信自建应用适配器，完成企业微信官方消息验签/解密、应用权限、可信入口、重试与事件去重。应用凭据与回调密钥由公司安全渠道配置，不放源码。
2. XLLoop所有者在问题与建议的“受理规则 / 企业微信接入进度”里，把企业微信UserID映射到已登录绑定的XLLoop成员。禁止按未验证邮箱自动建账号、扩权或信任用户消息指定的人员身份。
3. 在XLLoop服务端安全配置 `XLLOOP_FEEDBACK_BRIDGE_KEY`（随机至少32字符），适配器使用同一密钥对请求签名。
4. 私有Sites入口仍需平台认可的服务访问身份；不能仅为让回调进来把整个站点公开。独立部署后用公司的网关访问控制替换平台边界。
5. 验收入口到派单、补充、验收/重开、消息队列发出与回执；确认暂停、断网、重试不重复建单或盲目重复发送。

## XLLoop桥接协议

`POST /api/feedback/bridge`，Content-Type application/json。

- `X-XLLoop-Timestamp`：13位毫秒时间戳，容忍5分钟误差。
- `X-XLLoop-Signature`：小写十六进制 HMAC-SHA256(key, timestamp + '.' + 原始请求体)。必须使用实际发送的UTF-8字节，不可在签名后重新序列化。
- 这些是本项目自己的适配器协议，不是企业微信官方签名协议。

提交示例（无真实个人信息）：

```json
{"action":"submit","eventId":"official-event-unique-id","senderId":"verified-wecom-userid","project":"ybirds","title":"问题标题","description":"具体情况","category":"bug","priority":"normal","links":"https://company.example/evidence"}
```

senderId必须来自已经验签解密的企业微信消息，不可取自用户自然语言。project只能是该员工获授权项目；不确定传空字符串交统一入口。类别bug/improvement/opportunity。响应含id、number、status。eventId须稳定保留，重试使用相同值；不支持在此接口自动登录或批准业务动作。

适配器定时领取回告：

```json
{"action":"notifications"}
```

返回最多10条 `{id,recipient,text,ticket,deliveryToken}`。仅返回已经完成身份映射、仍获授权且能查看该工单的接收人。适配器向自己的企业微信应用发信，记录供应商回执后调用：

```json
{"action":"ack","id":"notification-id","deliveryToken":"returned-token","status":"sent","receipt":"provider-message-reference"}
```

status可为sent/failed/unknown。领取超时转unknown，不自动重发；适配器必须先核对供应商，再用原领取凭据确认。不得把网络超时当作未发送。无需发信或未有授权的环境只做站内通知，不调用外部发送。

## Agent辅助分诊

- 默认为关闭，项目负责人仍是结果责任人。
- 所有者按项目批准累计分诊预算和单次上限。台账包含实际费用和未知作业预留，不能清空策略来重置预算。
- 执行器新增固定任务 `triage_feedback`，声明 `feedback_triage` 能力，scope必须为analysis-only；不可读取生产写权限或根据用户输入执行命令。
- 正式立项项目还受已有的项目总预算和期限限制；供应商硬费用限制仍需适配器落实。
- 输入包含最少必要的反馈内容、证据链接；作为不可信资料处理。输出：`{status,summary,evidence,cost,suggestion:{category,priority,questions,duplicates:[ticketId]}}`。
- 自动/手动每次推进只派发或核对一个稳定ID。分类、重复和补充问题均为建议，不自动改派、不关闭、不批准新立项。负责人确认后操作。
- 真实模型/执行器尚需配置；测试中模拟响应不是已接通模型。
